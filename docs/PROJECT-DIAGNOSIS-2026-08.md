# OpenMusic 项目诊断与升级记录

更新时间：2026-08-30

## 当前状态

- 主分支为 `main`，代码、Release 与在线更新统一使用 GitHub 仓库 `yuchen0x1/JukeboxRoom`。
- 当前版本为 `2.0.1`，网站由 Express 托管，前端为 React/Vite，移动端为 Capacitor 远程 URL 壳。
- 已具备多人房间、实时播放同步、聊天室、三类音乐源、收藏/歌单、认证与 RBAC、管理接口、任务中心、AutoDJ、本地曲库、PWA 和 TV 页面。
- GitHub Release 已具备发行版本信息；iOS 构建需要 macOS/Xcode。
- Redis 是可选的生产持久化方案；未配置 Redis 时使用 JSON 文件存储，生产建议通过 `OPENMUSIC_DATA_DIR` 放在独立数据盘。
- 本轮已完成本地曲库元数据增强和可选目录监听，使用 `music-metadata` 与 `chokidar`，不改变默认关闭监听的部署行为。
- 本轮已完成音乐源健康状态和短时熔断，失败源会冷却后自动恢复探测，不改变现有音乐接口协议。

## 主要不足

1. 业务入口集中在较大的服务端入口和房间管理模块，进一步扩展前需要持续拆分路由、服务和存储边界。
2. 生产多实例依赖 Redis，当前仍应保持单实例运行；JSON 存储适合开发和小规模部署，不适合作为高并发主数据库。
3. 前端已有核心页面，但管理后台、曲库管理、AutoDJ 和共享歌单的完整操作界面仍不齐全。
4. 音乐上游依赖外部服务，播放、歌词和封面可用性受第三方接口、Cookie、版权和网络质量影响。
5. iOS 资产和签名发布仍需要 macOS 及 Apple 签名环境；移动端 CI 能力恢复后才能自动生成 IPA。
6. 当前自动化覆盖单元、接口和构建，浏览器端 E2E 需要可连接的浏览器扩展环境后再纳入 CI。

## 分阶段方案

### P0：可验证性与更新可靠性

- 在线版本检测固定使用 GitHub 官方源，其他镜像源不再作为更新通道。
- 对 Release 资产做官方域名校验，短暂上游故障时返回最近一次成功结果。
- 统一 `npm test`、`npm run check`、`npm run check:health` 检查入口。
- 为更新 API、通道回退、资产校验和客户端请求补充测试。

状态：已完成并通过真实测试、构建和临时实例健康检查。

### P1：部署与数据边界

- 支持 `OPENMUSIC_DATA_DIR`，将 JSON 数据与代码目录分离。
- 部署文档明确更新通道凭据、健康检查、数据目录和升级时不可覆盖的数据边界。
- CI 同时执行服务端和客户端测试、生产依赖审计与本地服务健康冒烟。

状态：已完成；Redis、多实例和备份恢复仍需生产环境单独演练。

### P1：音乐源可靠性

- 为网易云、QQ、酷狗请求记录成功/失败状态，连续失败达到阈值后短时熔断。
- 冷却结束只放行一次恢复探测，成功后清除失败计数。
- 通过 `/api/music/health` 提供不含密钥和用户数据的健康状态。

状态：已完成；真实第三方音乐源可用率仍需配置实际上游后持续观测。

### P2：产品完整性

- 补齐管理后台、曲库扫描/编辑、AutoDJ 控制和共享歌单页面。
- 为房间、账号、歌单和审计数据建立更明确的持久化模型及迁移路径。
- 增加浏览器 E2E、Socket 回归和上游服务降级测试。

状态：下一阶段，需按实际运营场景逐项实施。

### P3：跨平台发布与规模化

- 恢复或替换移动端 CI 能力，生成并上传 iOS IPA。
- 配置签名、校验和、发布说明和回滚流程。
- 在 Redis/数据库、备份、监控和告警完成后再评估多实例部署。

状态：受外部账号、macOS/Xcode 和生产基础设施约束，当前不自动执行。
