## 方案比较

| 能力 | JukeboxRoom 基线 | 对照和实现取舍 |
|---|---|---|
| 多人点歌和权限 | Socket.IO 房主、管理员、贵宾与排队投票 | Musare 分开 station 和 queue 数据，together 把访客申请与队列放在同一工作区。JukeboxRoom 保留已有角色，下一阶段改善手机队列切换和错误恢复。 |
| 同步和恢复 | 服务端播放时间、客户端偏差纠正和重连 | Syncplay 的客户端时钟与重连是质量对照，Snapcast 的多房间传输需要专用音频服务。保留按客户端获取音源的模型。 |
| 独立移动体验 | Android 本地搜索、队列及 Media3 桥；iOS 远程站点 | Opentune 的邀请面板分离输入、二维码和已加入状态。移动正式分发以同签名升级和后台音频真机验收为门槛。 |
| 自托管 | Node、JSON 存储、单实例或 Redis 辅助 | Navidrome 和 Music Assistant 强调源与部署独立；先完成官方版本包、哈希和容器冒烟。 |
| 更新与缓存 | 自动激活的 PWA、Windows NSIS、动态拉主分支 | Workbox 的等待激活模型用于本轮 PWA 交互。electron-builder 的 NSIS 方式需要确认签名配置，其下载进度和安装仍保留在原入口。 |
| UI | 大厅、房间工作区、移动播放器、TV 展示 | 保留品牌和分屏布局，借鉴 together 的触控回归、Opentune 的简短操作和 Workbox 的非阻塞更新；本轮新增明确的刷新与稍后操作。 |

重点实现路径包括 [together 时钟校准](https://github.com/chtnnh/together/blob/main/apps/web/src/lib/clock-sync.ts)、[together 手机队列测试](https://github.com/chtnnh/together/blob/main/apps/web/e2e/mobile-queue.spec.ts)、[Musare 房间模块](https://github.com/Musare/Musare)、[Opentune 的移动及共享会话目录](https://github.com/justshivv/Opentune)、[Syncplay 校时和重连](https://github.com/Syncplay/syncplay)、[Workbox 生命周期](https://developer.chrome.com/docs/workbox/service-worker-lifecycle) 和 [electron-builder Authenticode 配置](https://www.electron.build/code-signing)。本轮写入 JukeboxRoom 的实现来自现有架构和平台接口，没有导入这些项目的源码、品牌或媒体素材。
