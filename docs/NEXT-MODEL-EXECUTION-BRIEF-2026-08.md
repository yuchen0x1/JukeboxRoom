- 核心入口：`client/src/pages/Home.tsx`、`client/src/pages/Room.tsx`、`client/src/pages/TvDisplay.tsx`、`client/src/index.css`、`server/index.js`、`server/roomManager.js`。
- 已有完整的多人房间、实时同步播放、点歌/队列治理、聊天/图片/表情、歌词、收藏/历史、TV、封面/黑胶/3D 沉浸视觉、移动壳。不要重复造这些功能，也不要删掉已经工作的沉浸视觉。
- 现有技术债：`Room.tsx` 约 2793 行，`roomManager.js` 约 2922 行，`index.css` 约 3073 行；房间状态仍以进程内存为权威，JSON store 并发写不可靠；已有 Redis adapter 未完整接入；前端缺账号/后台等闭环。
- 已有深度审计和路线图：`docs/COMPREHENSIVE-UPGRADE-ROADMAP-2026-08.md`、`docs/FUNCTION-GAP-AUDIT.md`。先读它们，再决定每项的实际改动范围。
- 当前工作树已经有用户未提交改动：`.gitignore`、`server/admin/index.js`、`server/auth/index.js`、`server/db/store.js`、`server/index.js`、`server/auth/auth.test.js`、`server/playlists/`，以及两份未跟踪文档。绝不使用 reset、checkout 或删除它们；先读懂并在其基础上工作。

## 无图像识别模型的视觉基线

截图路径仅供人工复核：`docs/screenshots/home.png`、`docs/screenshots/room.png`、`docs/screenshots/lyrics.png`。

1. 首页（2560 x 1352）是深色房间大厅。现状：64px 左右的顶栏包含 OpenMusic 标志、昵称输入、加入/创建按钮和仓库图标；主体最大宽度约 1180px，但只有一张约 540px 宽的房间卡，页面其余区域严重空置；底部只有一行低对比说明。色彩是黑、灰、红，背景有模糊的红/紫光团。
2. 房间（2560 x 1352）是顶部房间状态栏 + 三栏工作台 + 固定底部播放器。左栏约 540px 为点歌热榜；中栏约 1245px 为搜索、队列和结果；右栏约 540px 为聊天。顶部显示房间号、音源/音质、纯净/背景、分享和退出；底部约 100px 显示封面、歌曲信息、进度与播放控制。空队列时中栏大面积空白，聊天表情面板挤压消息区，视觉密度与层级不平衡。
3. 歌词页（2560 x 1352）为左右二分：左边是黑胶唱片和唱臂，右边是歌曲名/歌手与垂直歌词；当前行最大且白色，邻行灰色；底部是一条进度条和居中的大圆形暂停按钮。这个方向合理，但封面、歌词、背景和控制区的关系仍像独立模块，没有统一的舞台氛围。

## 执行提示词

你是 OpenMusic 的主负责工程师和产品设计工程师。请在 `openmusic/` 内实际实施“V1.1 体验与可靠性升级”，不要只输出建议或计划。先审计现有代码、当前 git 工作树和 `docs/` 中的两份审计报告；保留用户已有改动，并在每个阶段完成后运行验证。你的目标是把已有功能密集但视觉粗糙、页面过大、单实例脆弱的多人实时音乐房，升级为快速、稳定、可维护、以歌曲封面与同步共听为核心的专业产品。

### 工作原则

1. 先运行并记录基线：`git status --short`、`npm run build --prefix client`、在 `server/` 运行 `node --test --test-concurrency=1`。遇到已有失败先定位，不要以跳过测试掩盖。
2. 不要重写整个项目，不要先拆微服务，不要改变已工作的 Socket 协议而没有兼容层。将每项变更控制为可验证的纵向闭环。
3. 遵循当前 React/TypeScript/Tailwind/Zustand/Lucide 模式。抽离真正复用的组件、hooks 和纯函数；不要只把巨型文件拆成大量无意义的小文件。
4. 所有工具按钮使用已有 `lucide-react` 图标与可访问标签/tooltip；保留文本按钮给“创建、保存、加入”等明确命令。键盘可达、焦点可见、错误/加载/空状态完整。
5. 不使用渐变光球、泛滥毛玻璃、巨大圆角卡片、营销式 landing page 或紫蓝单色主题。页面不是卡片套卡片；卡片仅用于房间、歌曲、消息、模态和真实独立工具。常规卡片/控件圆角不超过 8px。遵守 `prefers-reduced-motion`，低端设备或省电场景降级动画与 3D。

### 第一阶段：设计系统和用户体验（优先实际交付）

1. 建立可维护的基础 token（颜色、层级、边框、阴影、间距、字号、z-index、动效时长），逐步收敛 `index.css` 和分散的任意色值。主色使用珊瑚红作为“播放/危险/主操作”，以青绿或金色只做状态辅助；底色为接近黑的中性灰，文字有清晰的三级对比。不要依赖背景渐变撑视觉。
2. 重做首页为“可用的房间大厅”而非宣传页：紧凑顶部工具栏；房间网格在 1440px 可显示 3-4 个高信息密度房间；每张卡以当前曲目的真实封面、播放状态、房间人数、队列、锁定状态和最近访问为主体；空房间使用清晰的建立房间操作。首屏能看见房间内容和下一行内容，不能出现截图中大面积空白。
3. 重构房间的桌面信息架构：左侧为可收起的发现/热榜，中央为搜索、队列与歌词/播放主工作区，右侧为可收起聊天；保留固定的紧凑播放器。给空队列一个有用的下一步（搜索、热榜、歌单、AutoDJ 状态），而不是黑色空区。聊天表情/贴纸选择器必须为弹层或抽屉，不能长时间压缩消息列表。
4. 重构移动端：默认只保留最重要的点歌/当前播放工作区；队列、热榜、聊天、房间成员以抽屉/底部 sheet 打开；播放器固定且不遮挡输入；点击目标至少 44px；375px、768px、1440px 和 2560px 下无横向溢出、文字截断或重叠。
5. 以真实歌曲封面为视觉锚点：复用并强化 `SongCover`、`coverUrl`、`coverBackdrop` 的加载、失败占位、尺寸、`alt` 和预加载策略；从封面提取的颜色必须有中性遮罩与文本对比保护。禁止用 AI 生成的无关装饰图替代实际歌曲/房间内容。
6. 保留并统一黑胶、歌词、TV、星河、地形等沉浸模式的视觉语言：沉浸模式是全屏主体验，不被装进装饰卡；控制层保持低干扰；所有 WebGL/CSS 特效可通过性能等级降级，且不应阻塞正常点歌、聊天或同步。

### 第二阶段：速度、流畅度与维护性

1. 用 `vite build` 输出作为依据，清除假懒加载（同组件又静态又动态引入）和重复依赖；按路由/功能懒加载重量模块，尤其是聊天、复杂设置、3D 视觉和非首屏列表。不得让基础房间操作等待 Three.js 或 MediaPipe 下载。
2. 为长列表采用已有 `react-window` 或等价虚拟化策略；避免房间全状态变化时无关组件重渲染；为封面使用尺寸稳定、延迟加载、解码失败回退和请求去重。不要为了“优化”破坏实时歌词与播放进度的平滑度。
3. 给动画、滚动、聊天图片、频谱/3D 设置明确帧率/并发预算；按 `visibilitychange`、`prefers-reduced-motion` 和设备能力暂停或降级后台工作。用 `PerformanceObserver` 或轻量性能标记收集真实指标，避免只写理论结论。
4. 把 `Room.tsx`、`useSocket.ts` 的新增工作分成领域明确的组件/Hook，并通过 selector、memo 和稳定回调避免全页重渲染。每次拆分后验证房间进入、搜索、加歌、播放/暂停、聊天、重连和移动端导航。

### 第三阶段：先补 P0 可靠性，再扩功能

1. 先审查当前未提交的 `server/auth`、`server/db`、`server/admin` 改动。确保公开注册永远只能创建普通用户，生产环境没有默认 JWT 密钥，角色变更和敏感后台操作有服务器端授权和审计。为这些规则补测试。
2. 处理 JSON 存储并发损坏风险。若本轮无法安全完成数据库迁移，至少实现原子写、串行写队列、损坏恢复/备份与并发测试，并把 PostgreSQL/SQLite WAL 迁移列为下一个有验收标准的任务；不能把同步整文件读写继续当生产可靠方案。
3. 完成最小运营闭环：真实在线房间从 `roomManager` 暴露给管理员，管理员可安全查看房间、执行受审计的关闭/治理操作；不要保留返回空数组的假后台接口。
4. 仅在协议版本、幂等、重连恢复和两实例测试方案明确后，启用/完善 Redis adapter 与房间 lease。把播放、成员、聊天等状态逐步改为 snapshot/patch/resync，保留旧客户端兼容路径；不要直接把内存房间 Map 粗暴地分布式化。
5. 把 AutoDJ 从孤立 API 接到“队列为空/播放结束”的真实房间事件，具备开关、可解释的选歌来源、最近播放避重和失败回退。不要先做不受控 AI DJ。

### 明确不做

- 在账号、数据、权限、测试、观测和内容授权没有基础前，不收费、不做插件市场、不做微服务/区块链/元宇宙，也不把第三方音乐/歌词/封面当可商用资产。
- 不删除现有外部音源、TV、沉浸视觉、房间治理或 Capacitor 工程；新功能必须有渐进式降级。
- 不把视觉升级变成单纯加阴影、模糊、渐变或动画。优先信息层级、真实封面、空状态、响应式和性能。

### 任务顺序与验收

按以下顺序实施，并在每步结束时列出修改文件、行为变化、风险和已运行命令：

1. 基线审计与性能测量。
2. Token/通用控件与首页大厅升级。
3. 房间桌面与移动布局升级、空状态、封面和聊天抽屉。
4. 懒加载、渲染控制、长列表/媒体性能优化。
5. 认证/RBAC、原子存储、最小后台与审计测试。
6. AutoDJ 接入与可观测性基础。
7. Redis 多实例协议设计与独立实现任务。只有前六项稳定后才进入此项。

每个提交前至少通过：前端 `npm run build --prefix client`；服务端在 `server/` 中 `node --test --test-concurrency=1`；新增的关键纯函数与安全规则有测试；桌面和移动端无可见横向滚动、悬浮层遮挡输入或文字重叠。用浏览器自动化/DOM 断言验证关键流程和断点，即使你不能看截图，也要用固定 viewport、语义标签、尺寸约束和可访问性断言验证布局。最终交付不能只说“已优化”，必须给出前后构建体积/性能观测、功能验证结果、遗留风险与下一阶段建议。

## 人工复核问题

下一位模型没有视觉能力时，以下项目需在每个 UI 里程碑后由人工打开确认：封面与文本对比度是否足够、沉浸模式的动效是否舒适、真实音乐数据是否造成长文本截断、聊天抽屉是否符合使用习惯。模型应在报告中明确标记这些人工复核点，而不是假装已经看过截图。
